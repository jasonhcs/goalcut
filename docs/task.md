### Demo 验证阶段说明

> **Phase 0 和 Phase 1 为 Demo 验证阶段**，目标是以最低成本快速跑通核心链路。
>
> **核心原则：零外部依赖、纯命令行验证**
> - **不引入** PostgreSQL / MySQL 等数据库
> - **不引入** Redis / NATS / RabbitMQ 等消息队列
> - **不引入** MinIO / S3 等对象存储
> - **不引入** Docker → 直接 `go run` + `python` 本地启动
> - **不引入** Web 前端 → Phase 1 为纯命令行工具，验证「视觉检测进球 → 生成集锦」核心能力
>
> Phase 1 的目标是：**给定一个本地篮球视频文件，自动检测所有进球瞬间，输出进球前后各 3 秒的拼接集锦视频。**

## 三点五、Phase 1.5 — 检测算法优化（P1 核心）

> **核心目标**：在 Phase 1 MVP 基础上，针对**野球场/业余比赛**场景大幅提升进球检测准确率，不改变 CLI 工具形态，不引入 Web 应用。
>
> **背景**：Phase 1 MVP 采用硬编码 ROI + 启发式规则，在非标准机位下准确率仅 50~60%，远低于产品目标（Precision ≥ 80%, Recall ≥ 75%）。
>
> **详细设计**：参见 `docs/进球检测算法.md` 第十一章"当前实现状态与优化路线"。
>
> 预计工期：2～3 周

## 九、注意事项

1. **零依赖启动**：Phase 0/1/1.5 Demo 阶段严禁引入外部组件，确保 `go run` + `python` + FFmpeg 即可跑通
2. **先验证核心算法**：Phase 1 聚焦视觉检测进球的核心能力验证，不做 Web 应用、不做数据持久化，用最短路径验证「YOLO 检测篮球进筐」是否可行
3. **Phase 1.5 先于 Phase 2**：在进入 Web 应用开发之前，必须先通过 Phase 1.5 将检测算法准确率提升到产品可用水平（野球场 F1 ≥ 77%），否则 Web 应用无意义
4. **接口抽象优先**：Phase 2 引入 Web 应用时，所有 Store/Queue/FileStorage 必须先定义接口再实现内存版本，为后续持久化迁移打基础
4. **依赖优先**：严格按依赖链推进，Phase 0 阻塞所有后续任务
5. **数据先行**：数据集收集标注（T-1.2.1）应尽早启动，可与 Phase 0 并行准备
6. **并行开发**：同阶段内无依赖关系的模块应并行推进（如 Phase 2 中 T-2.2/T-2.3/T-2.4 可同时开发）
7. **风险预警**：标注了"核心算法，需反复调优"的任务（如 T-1.3.2 进球轨迹判定）预留额外缓冲时间
8. **持续集成**：每个子任务完成后及时更新本文档状态
9. **迁移时机**：Phase 3 的 T-3.6（外部组件迁移）应在该阶段最先执行，其他功能依赖持久化存储
