## 一、概述

### 1.1 核心问题

篮球进球检测的本质是一个**视频事件识别问题**：在连续的视频流中，判断某一时刻篮球是否穿越篮筐进入篮网，并精确定位该事件的时间戳。

这一问题的核心难点在于：

- **信号稀疏**：一场 90 分钟比赛中进球事件只有 40~80 次，仅占总帧数的极小比例
- **场景差异大**：正式比赛有记分牌、多机位、解说员；野球场仅有单机位固定视角，无任何辅助信息
- **视觉干扰多**：球员遮挡、球体运动模糊、镜头抖动、光线变化等
- **单一信号不可靠**：任何单一检测维度都存在误报或漏报

GoalCut 采用**多模态信号融合 + 场景自适应权重**的策略，综合多维度信号进行进球判断。

### 1.2 市场竞品对比

在研究 GoalCut 算法之前，先梳理市场上主流产品的进球检测思路：

| 产品 | 核心方法 | 准确率 | 适用场景 | 局限 |
|------|---------|--------|---------|------|
| **Second Spectrum**（NBA 官方） | 多摄像头 3D 光学追踪，重建球的三维轨迹穿越篮筐平面 | ~100% | 职业赛场（需固定安装 6+ 摄像头） | 硬件成本极高，不可移植 |
| **WSC Sports** | 记分牌 OCR 为主信号，叠加解说 NLP + 欢呼声 + 镜头切换 | >99% | 正式比赛直播信号 | 强依赖记分牌和直播数据流 |
| **Pixellot** | 全景拼接摄像头 + 运动跟踪 AI，检测球在篮筐区域的轨迹 | ~95% | 需固定安装全景摄像头 | 依赖专有硬件 |
| **HomeCourt**（面向个人） | 单摄像头视觉追踪，检测球穿越篮筐 ROI 且方向向下 | 85~95% | 单机位固定视角，环境要求严格 | 遮挡/光线差时准确率下降 |
| **学术/开源方案** | YOLO 检测 + 轨迹追踪 + 几何判断，帧差分辅助 | ~95% | 通用场景 | 遮挡/对抗时误判率高 |

**核心观察**：

1. 所有成熟产品都采用多信号融合策略，没有任何单一方法是完美的
2. 记分牌 OCR 是正式比赛中准确率最高的信号（接近 100%），但对野球场完全无效
3. **野球场单机位场景目前市面上没有成熟的商业产品**，是 GoalCut 的核心差异化机会
4. 竞品几乎不使用篮网形变检测和入网声检测，这是 GoalCut 可以利用的独特信号

## 二、场景模式与检测策略

### 2.1 两种场景的信号差异

GoalCut 需要同时适配两种截然不同的场景：

| 信号维度 | 正式比赛 | 野球场 | 备注 |
|---------|---------|--------|------|
| 记分牌 | ✅ 有（画面固定位置） | ❌ 无 | 野球场核心缺失 |
| 解说员 | ✅ 有 | ❌ 无 | — |
| 多机位/回放 | ✅ 有（进球后常有回放） | ❌ 无 | — |
| 观众欢呼声 | ✅ 有（大量观众） | △ 弱（少数球友） | 信号强度差异大 |
| 篮球入网声 | △ 有（但被环境声掩盖） | ✅ 较清晰（安静场地） | — |
| 球友叫好/击掌 | ❌ 无 | ✅ 有 | — |
| 篮球/篮筐视觉 | ✅ 有（固定机位或跟拍） | ✅ 有（固定单机位） | 共有信号 |
| 篮网形变 | ✅ 有 | ✅ 有 | 共有信号，野球场更明显 |

### 2.2 场景自动识别

系统在处理视频开始时，自动分析视频前 10 秒，判断场景类型：

```python
def detect_scene_mode(video_path: str) -> str:
    """
    分析视频前 10 秒，判断场景类型。
    返回: 'official'（正式比赛）或 'pickup'（野球场）
    """
    has_scoreboard = detect_scoreboard_region(video_path, duration=10)
    has_multi_camera = detect_camera_switches(video_path, duration=10)

    if has_scoreboard or has_multi_camera:
        return 'official'
    return 'pickup'
```

用户也可以手动指定场景模式，覆盖自动识别结果。

### 2.3 动态权重分配

根据场景模式，各检测维度的权重动态调整：

| 检测维度 | 正式比赛权重 | 野球场权重 | 调整原因 |
|---------|------------|-----------|---------|
| 记分牌 OCR | **0.40** | 0.00（禁用） | 野球场无记分牌 |
| 视觉轨迹检测 | 0.30 | **0.70** | 野球场主力检测手段 |
| 篮网形变检测 | 0.00 | **0.20** | 进球后篮网晃动，野球场更清晰 |
| 音频分析 | 0.15 | 0.10 | 野球场仅检测入网声/叫好声 |
| 场景变化检测 | 0.15 | 0.00（禁用） | 野球场无回放/慢动作 |

## 三、检测流水线总览

```
原始视频输入
    │
    ├─── [阶段 0] 场景模式识别
    │    └─ 分析前 10s，自动判定 official / pickup
    │
    ├─── [阶段 1] 预处理
    │    ├─ FFmpeg 视频解码
    │    ├─ 关键帧提取（2~5 fps 自适应采样）
    │    └─ 音频轨道分离
    │
    ├─── [阶段 2] 并行多模态检测（根据场景模式启用/禁用各 Pipeline）
    │    │
    │    ├─ Pipeline A：视觉轨迹检测（所有模式）
    │    │   ├─ YOLO 检测篮球 + 篮筐 + 球员
    │    │   ├─ ByteTrack 追踪篮球运动轨迹
    │    │   └─ 几何判断：球穿越篮筐平面且方向向下 → 进球候选
    │    │
    │    ├─ Pipeline B：篮网形变检测（野球场模式增强）
    │    │   ├─ 定位篮网 ROI 区域
    │    │   ├─ 光流法 / 帧差分计算该区域运动量
    │    │   └─ 运动量超过阈值 → 篮网晃动候选
    │    │
    │    ├─ Pipeline C：记分牌 OCR（仅正式比赛模式）
    │    │   ├─ 自动定位记分牌区域
    │    │   ├─ PaddleOCR 识别比分数字
    │    │   └─ 分数跳变 → 得分事件
    │    │
    │    ├─ Pipeline D：音频分析（所有模式，策略不同）
    │    │   ├─ 正式比赛：欢呼声音量峰值 + 解说激动度
    │    │   └─ 野球场：入网声（Swish）+ 球友叫好/击掌声
    │    │
    │    └─ Pipeline E：场景变化检测（仅正式比赛模式）
    │        ├─ 镜头切换检测（硬切/渐变）
    │        └─ 慢动作回放检测
    │
    ├─── [阶段 3] 多模态融合
    │    ├─ 时间轴对齐（各维度结果对齐到统一时间轴）
    │    ├─ 加权融合置信度（动态权重）
    │    ├─ 阈值过滤（默认阈值 0.5）
    │    └─ 事件去重与合并（同一进球的多次检测合并）
    │
    └─── [阶段 4] 输出
         └─ 进球事件列表 [{timestamp, score_type, confidence, detections}]
```

## 四、各检测维度详解

### 4.1 视觉轨迹检测（Pipeline A）

视觉轨迹检测是所有场景的核心检测手段，在野球场模式下权重高达 0.70。

#### 4.1.1 目标检测

使用 **YOLOv8** 对每帧（采样帧）进行目标检测，检测以下类别：

| 检测目标 | 说明 | 用途 |
|---------|------|------|
| `basketball` | 篮球 | 轨迹追踪 |
| `hoop` | 篮筐/篮圈 | 确定进球区域 |
| `net` | 篮网 | 形变检测 ROI |
| `player` | 球员 | 遮挡处理，辅助判断投篮类型 |

#### 4.1.2 目标追踪

使用 **ByteTrack** 对篮球进行跨帧追踪，输出带 ID 的球体轨迹序列：

```
轨迹点序列: [(t₁, x₁, y₁, conf₁), (t₂, x₂, y₂, conf₂), ...]
```

追踪策略：
- 置信度低于 0.3 的检测框不参与追踪初始化，但可用于补全轨迹（ByteTrack 二阶段匹配）
- 追踪丢失超过 1 秒则终止该轨迹，等待重新初始化

#### 4.1.3 进球几何判定

这是视觉检测的核心逻辑，参考竞品（HomeCourt、学术方案）的最佳实践，采用**严格几何判断**而非简单区域包含：

```python
def judge_goal_by_trajectory(trajectory: List[Point], hoop: Rect) -> GoalResult:
    """
    通过球体轨迹判断是否进球。

    判定条件（需同时满足）：
    1. 球体轨迹在篮筐区域上方出现
    2. 球体运动方向向下（Y 轴坐标递增）
    3. 球体中心穿越篮筐内圈平面（水平线 y = hoop.center_y）
    4. 穿越点的 X 坐标在篮筐内圈范围内（hoop.left ~ hoop.right）
    5. 连续至少 3 帧满足以上条件（防误判）
    """
    crossing_frames = []

    for i in range(1, len(trajectory)):
        prev, curr = trajectory[i-1], trajectory[i]

        # 条件2：方向向下
        if curr.y <= prev.y:
            continue

        hoop_y = hoop.center_y
        # 条件3：穿越篮筐水平线
        if not (prev.y < hoop_y <= curr.y):
            continue

        # 线性插值计算穿越时的 X 坐标
        ratio = (hoop_y - prev.y) / (curr.y - prev.y)
        cross_x = prev.x + ratio * (curr.x - prev.x)

        # 条件4：穿越点在篮筐内圈范围内（加容差 ±10%）
        margin = hoop.width * 0.1
        if hoop.left - margin <= cross_x <= hoop.right + margin:
            crossing_frames.append(i)

    # 条件5：连续帧确认
    if len(crossing_frames) >= 2:
        goal_timestamp = trajectory[crossing_frames[0]].time
        confidence = min(1.0, len(crossing_frames) / 3.0)
        return GoalResult(detected=True, timestamp=goal_timestamp, confidence=confidence)

    return GoalResult(detected=False)
```

**关键设计决策**：

> 竞品的主要误判来源之一是"球在篮筐附近但未进"的场景（如擦框弹出、篮下对抗）。采用**方向向下 + 穿越内圈平面**的严格几何判断，可以有效排除这类误判。

#### 4.1.4 冷静期机制

进球确认后设置 **2 秒冷静期**，期间忽略新的进球候选，防止同一进球被重复计数（球弹网多次触框）。

### 4.2 篮网形变检测（Pipeline B）

篮网形变检测是 GoalCut 的**差异化特色信号**，市面竞品几乎不使用，在野球场模式下权重为 0.20。

**物理原理**：篮球进网后，篮网受到冲击会产生明显的形变和晃动，这是进球的可靠物理信号，即使在球体检测置信度低的情况下也能生效。

#### 4.2.1 篮网 ROI 定位

```python
def get_net_roi(hoop: Rect, frame_height: int) -> Rect:
    """
    根据篮筐位置推算篮网 ROI 区域。
    篮网位于篮筐下方，高度约为篮筐宽度的 1.5 倍。
    """
    return Rect(
        left=hoop.left - hoop.width * 0.1,
        top=hoop.center_y,
        right=hoop.right + hoop.width * 0.1,
        bottom=min(hoop.bottom + hoop.width * 1.5, frame_height)
    )
```

#### 4.2.2 形变量计算

##### v1（T-1.9.7）：平均光流幅度（旧版，已降级为回退方案）

使用**Farneback 稠密光流法**计算篮网 ROI 区域内的平均像素运动量：

```python
def calc_net_deformation(frame_prev: np.ndarray, frame_curr: np.ndarray,
                          net_roi: Rect) -> float:
    """
    计算篮网区域的形变量（归一化到 0~1）。
    返回值越大，篮网晃动越明显。
    局限：无法区分进球（垂直向下穿越）与篮板争抢（横向混乱运动）。
    """
    roi_prev = crop_roi(frame_prev, net_roi)
    roi_curr = crop_roi(frame_curr, net_roi)
    gray_prev = cv2.cvtColor(roi_prev, cv2.COLOR_BGR2GRAY)
    gray_curr = cv2.cvtColor(roi_curr, cv2.COLOR_BGR2GRAY)

    flow = cv2.calcOpticalFlowFarneback(
        gray_prev, gray_curr, None,
        pyr_scale=0.5, levels=3, winsize=15,
        iterations=3, poly_n=5, poly_sigma=1.2, flags=0
    )
    magnitude = np.sqrt(flow[..., 0]**2 + flow[..., 1]**2)
    avg_magnitude = np.mean(magnitude)
    return min(1.0, avg_magnitude / 5.0)
```

##### v2（T-1.9.13）：有向光流穿越检测（算法C，当前默认）

**核心改进**：计算篮网 ROI 区域的**垂直向下光流分量**与**横向分量**之比（方向纯净度），直接区分进球与篮板争抢：

```python
def compute_directional_flow(prev_gray, curr_gray, roi) -> Tuple[float, float, float]:
    """
    计算 ROI 区域的有向光流特征。
    返回 (downward_score, horizontal_noise, directional_purity):
      - downward_score:  垂直向下光流分量均值
      - horizontal_noise: 横向光流分量绝对值均值
      - directional_purity: 方向纯净度 = downward / (horizontal + eps)
        进球时 >> 1（纯向下穿越）
        篮板争抢时 ≈ 0.5~1.0（横向混乱）
    """
    flow = cv2.calcOpticalFlowFarneback(prev_roi, curr_roi, ...)
    vx, vy = flow[..., 0], flow[..., 1]
    downward_score = float(np.mean(np.clip(vy, 0, None)))   # 只统计向下
    horizontal_noise = float(np.mean(np.abs(vx)))
    directional_purity = downward_score / (horizontal_noise + 1e-6)
    return downward_score, horizontal_noise, directional_purity
```

**事件判定条件**（双重过滤）：

1. **下行光流突发**：`downward_score > mean + 2.0 × std`（突发阈值）
2. **方向纯净度** ≥ 1.5：向下分量必须是横向分量的 1.5 倍以上
3. **后续衰减验证**：峰值后 3 帧内光流需减弱到 80% 以下（球已穿过）

**置信度计算**：结合突发强度 + 纯净度贡献，基础分 0.35，上限 0.70。

**降级策略**：新版有向光流检测失败时自动回退到 v1 平均幅度检测，确保健壮性。

#### 4.2.3 形变事件判定

v2（有向光流）的判定已内置于 `detect_downward_flow_through_net()` 中，包含冷静期（3s）、突发检测、方向纯净度过滤和后续衰减验证，输出带 `frame_index`、`timestamp`、`confidence`、`detail` 的事件列表。

**注意事项**：

- ~~篮板球争抢时篮网也可能晃动，单独依赖此信号误报率较高~~ → v2 通过方向纯净度已大幅缓解此问题
- 篮板争抢的横向运动特征（directional_purity ≈ 0.5~1.0）会被自动过滤
- 正式比赛模式下此信号权重仍设为 0，避免与 OCR 信号产生干扰

#### 4.3.2 分数识别与变化检测

```python
def detect_score_change(
    ocr_results: List[TimedScore]
) -> List[ScoringEvent]:
    """
    对比相邻帧的 OCR 识别结果，检测分数跳变。

    处理策略：
    - OCR 结果先经过噪声过滤（去除明显错误的识别结果）
    - 分数只能递增（篮球规则），逆向跳变为 OCR 错误
    - 跳变量为 1、2、3（1分/2分/3分球）时确认为进球
    - 跳变量为其他值时标记为疑似 OCR 错误，降低置信度
    """
    events = []
    for i in range(1, len(ocr_results)):
        prev_score = ocr_results[i-1]
        curr_score = ocr_results[i]
        delta = curr_score.home - prev_score.home  # 以主队为例

        if delta in (1, 2, 3):
            score_type = {1: 'free_throw', 2: 'two_pointer', 3: 'three_pointer'}[delta]
            events.append(ScoringEvent(
                timestamp=curr_score.time,
                score_type=score_type,
                confidence=0.95 if delta in (2, 3) else 0.85
            ))
    return events
```

#### 4.4.2 正式比赛模式：欢呼声 + 解说激动度

## 五、多模态融合算法

### 5.1 时间轴对齐

各 Pipeline 的检测结果被对齐到统一的时间轴，以秒为单位，精度为 0.1 秒：

```python
def align_to_timeline(
    visual_events: List[Event],
    net_events:    List[Event],
    ocr_events:    List[Event],
    audio_events:  List[Event],
    scene_events:  List[Event],
    video_duration: float,
    resolution: float = 0.1  # 时间轴分辨率（秒）
) -> np.ndarray:
    """
    将各维度事件映射到统一时间轴，返回各维度的置信度时间序列。
    每个时间点的置信度 = 该时间点附近（±0.5s）最高事件置信度
    """
```

### 5.2 置信度融合

```python
WEIGHT_PRESETS = {
    'official': {
        'ocr':        0.40,
        'visual':     0.30,
        'net_deform': 0.00,
        'audio':      0.15,
        'scene':      0.15,
    },
    'pickup': {
        'ocr':        0.00,
        'visual':     0.70,
        'net_deform': 0.20,
        'audio':      0.10,
        'scene':      0.00,
    },
}

def fuse_confidence(
    visual_score:     Optional[float],
    net_deform_score: Optional[float],
    ocr_score:        Optional[float],
    audio_score:      Optional[float],
    scene_score:      Optional[float],
    scene_mode:       str = 'official'
) -> float:
    """
    根据场景模式动态选择权重，融合各维度置信度。
    None 表示该维度在当前帧未触发，不参与计算（权重归零处理）。
    """
    weights = WEIGHT_PRESETS[scene_mode]
    scores  = {
        'ocr':        ocr_score,
        'visual':     visual_score,
        'net_deform': net_deform_score,
        'audio':      audio_score,
        'scene':      scene_score,
    }

    total_weight = 0.0
    total_score  = 0.0

    for key, score in scores.items():
        w = weights[key]
        if score is not None and w > 0:
            total_weight += w
            total_score  += w * score

    if total_weight == 0:
        return 0.0

    fused = total_score / total_weight

    # 正式比赛：OCR 高置信度时给予额外加成（最可靠信号）
    if scene_mode == 'official' and ocr_score is not None and ocr_score > 0.8:
        fused = min(1.0, fused * 1.2)

    # 野球场：视觉轨迹 + 篮网形变双高置信度时给予额外加成
    if scene_mode == 'pickup':
        if (visual_score is not None and visual_score > 0.7 and
                net_deform_score is not None and net_deform_score > 0.7):
            fused = min(1.0, fused * 1.15)

    return fused
```

### 5.3 事件去重与合并

同一次进球可能被多个 Pipeline 在相近时间点各自检测到，需要合并为单一事件：

```python
DEDUP_WINDOW = 3.0  # 去重时间窗口（秒）

def deduplicate_events(events: List[FusedEvent]) -> List[GoalEvent]:
    """
    对时间相近的事件进行去重合并。
    策略：
    1. 按时间戳排序
    2. 相邻事件时间差 < DEDUP_WINDOW 则合并（取置信度最高的时间戳）
    3. 输出最终进球事件列表
    """
    if not events:
        return []

    events.sort(key=lambda e: e.timestamp)
    merged = [events[0]]

    for event in events[1:]:
        if event.timestamp - merged[-1].timestamp < DEDUP_WINDOW:
            # 合并：保留置信度更高的时间戳
            if event.confidence > merged[-1].confidence:
                merged[-1] = event
        else:
            merged.append(event)

    return merged
```

### 5.4 最终过滤

```python
CONFIDENCE_THRESHOLD = 0.5  # 最终置信度阈值（可配置）

def filter_events(events: List[GoalEvent], threshold: float = CONFIDENCE_THRESHOLD) -> List[GoalEvent]:
    """过滤低置信度事件，输出最终进球列表"""
    return [e for e in events if e.confidence >= threshold]
```

## 七、已知局限与误判来源

### 7.1 视觉轨迹检测的误判场景

| 场景 | 误判类型 | 应对策略 |
|------|---------|---------|
| 篮下激烈对抗 | 误报（FP）：球在篮筐区域反复出现 | 严格几何判断（穿越内圈平面 + 方向向下） |
| 球被球员遮挡 | 漏报（FN）：追踪丢失 | ByteTrack 二阶段匹配补全轨迹 |
| 擦框未进 | 误报（FP）：球触筐弹出 | 连续 3 帧确认 + 冷静期机制 |
| 远景三分球 | 漏报（FN）：球体检测置信度低 | 降低远景场景的检测阈值（待优化） |
| 竖版视频 | 误报/漏报：ROI 区域计算偏差 | 视频旋转检测 + ROI 自适应调整 |

### 7.2 篮网形变检测的误判场景

| 场景 | 误判类型 | 应对策略 |
|------|---------|---------|
| 篮板球争抢 | 误报（FP）：碰框导致篮网晃动 | ~~权重低（0.20），与视觉轨迹联合判断~~ → v2.5 有向光流方向纯净度过滤（T-1.9.13），横向混乱运动自动排除 |
| 风吹/外力 | 误报（FP）：室外环境 | 引入基线运动量校准；有向光流的突发阈值（mean+2σ）可过滤持续性低幅度运动 |

### 7.3 音频分析的误判场景

| 场景 | 误判类型 | 应对策略 |
|------|---------|---------|
| 背景噪音 | 误报（FP）：噪音被误识别为欢呼/入网声 | 权重低（≤0.15），仅作辅助信号 |
| 多人同时发声 | 漏报（FN）：信号被掩盖 | — |

### 7.4 记分牌 OCR 的误判场景

| 场景 | 误判类型 | 应对策略 |
|------|---------|---------|
| 记分牌遮挡/切换 | 漏报（FN）：无法读取 | 结合视觉轨迹兜底 |
| OCR 误识别 | 误报（FP）：数字识别错误 | 分数只增不减的合法性校验 |

## 十一、当前实现状态与优化路线

> 本章基于 Phase 1 MVP 的实际代码（`ai-engine/detect.py`、`internal/ffmpeg/ffmpeg.go`、`configs/config.yaml`），对比上述目标架构，梳理差距并规划分阶段优化路径。

### 11.1 Phase 1 MVP 实现现状

Phase 1 已完成的 MVP 是一个**纯视觉、单维度、启发式**的进球检测方案，核心实现如下：

| 维度 | MVP 实际实现 | 目标架构（本文档设计） |
|------|-------------|---------------------|
| **目标检测模型** | YOLOv8n 预训练模型，检测 COCO class 32（sports ball）| 篮球专用模型，同时检测 basketball / hoop / net / player |
| **篮筐定位** | 硬编码 ROI：画面高度 15%~65% 范围 | YOLO 动态检测 hoop 目标，实时定位篮筐 |
| **目标追踪** | 无追踪器，仅帧间球位置比较 | ByteTrack 跨帧追踪，带 ID 的轨迹序列 |
| **进球判定** | 两种启发式规则：① 球在 ROI 连续出现后消失 ② 球 Y 坐标急剧下降 | 严格几何判断：球穿越篮筐内圈平面 + 方向向下 + 连续帧确认 |
| **篮网形变** | ❌ 未实现 | 光流法检测篮网 ROI 运动量 |
| **记分牌 OCR** | ❌ 未实现 | PaddleOCR 分数识别与跳变检测 |
| **音频分析** | ❌ 未实现；且集锦视频裁剪使用 `-an` 丢弃音轨 | 入网声 / 欢呼声 / 叫好声多目标检测 |

| **多模态融合** | ❌ 仅单维度视觉 | 五维度加权融合 + 动态权重 |

### 11.2 核心差距分析

基于 GoalCut **野球场/业余比赛自动集锦**的产品定位，对当前 MVP 与目标架构的差距按影响程度排序：

#### 差距 1：硬编码 ROI — 最大准确率瓶颈 🔴

```python
# 当前代码 (detect.py L141-142)
hoop_y_min = img_h * 0.15
hoop_y_max = img_h * 0.65
```

**问题**：野球场拍摄角度多变（高位/低位/侧面），固定比例 ROI 在非标准机位下会严重偏移，导致大量漏检和误判。

**影响**：Precision/Recall 均受限，预估当前准确率仅 50~60%，远低于目标 80%+。

#### 差距 2：无目标追踪 — 进球判定逻辑脆弱 🔴

当前仅做帧间球位置比较，无法：
- 区分多个球体（野球场常有多个球）
- 在遮挡后重新关联同一球体
- 构建完整抛物线轨迹用于几何判定

#### 差距 3：集锦无音频 — 体验缺失 🟡

```go
// 当前代码 (ffmpeg.go L158)
"-an",  // 丢弃音轨
```

**问题**：集锦视频完全没有声音，对于野球场场景（球友叫好、入网声）严重影响观看体验。

#### 差距 4：置信度阈值过低 — 误报偏多 🟡

```yaml
# 当前配置 (config.yaml)
confidence_threshold: 0.3
yolo_confidence: 0.3
```

**问题**：0.3 的阈值使得大量低质量检测结果被当作进球候选，误报率高。

#### 差距 5：无篮网形变 / 音频辅助 — 缺少野球场差异化信号 🔵

野球场模式下，篮网形变（权重 0.20）和入网声（权重 0.10）是重要辅助信号，当前完全缺失。

### 11.3 优化项与优先级

根据**成本收益比**（准确率提升 / 开发成本），将优化项分为三个优先级：

#### P1 — 核心提升（预计 40h，改进检测架构）

| O-3 | **动态篮筐检测** | 在 YOLO 检测中增加 hoop 类别（使用开源篮球数据集微调或 Roboflow 预训练权重），替代硬编码 ROI | **最关键优化**，Recall 预估提升 20%+ |
| O-4 | **基于空间几何的进球判定** | 实现本文档 4.1.3 节的 `judge_goal_by_trajectory` 算法：球穿越篮筐平面 + 方向向下 + X 坐标在内圈范围 | Precision 预估提升 15%，有效排除"球在篮筐附近但未进"的误判 |

#### P2 — 差异化增强（预计 30h，多模态扩展）

| 编号 | 优化项 | 改动 | 预期效果 |
|------|--------|------|---------|
| O-7 | **篮网形变检测** | 实现本文档 4.2 节的 Pipeline B：光流法计算篮网 ROI 运动量 | 野球场模式下提供 0.20 权重的辅助信号 |
| O-8 | **入网声（Swish）检测** | 提取音频轨道，使用 Mel 频谱 + 短时能量检测短促高频脉冲 | 野球场安静环境下的独特辅助信号 |
| O-9 | **两阶段采样** | 第一遍低帧率（2fps）粗扫 → 锁定候选区间 → 第二遍高帧率（8fps）精确检测 | 在不增加总耗时的情况下提高时间定位精度 |
| O-10 | **篮球专用 YOLO 模型** | 收集/标注篮球场景数据集，微调 YOLOv8 检测 basketball/hoop/net/player 四类 | 从根本上提升检测精度，配合动态篮筐检测 |

### 12.2 当前算法在野球场场景的核心瓶颈

#### 瓶颈 1：采样率与球穿越篮筐时间窗口的物理冲突 🔴

```
球穿越篮筐平面的时间：约 0.1~0.3 秒
3fps 帧间隔：              约 0.33 秒
结论：穿越帧极大概率被漏采
```

通道 1a 的几何穿越判定（`judge_goal_by_trajectory`）要求捕捉到「球在篮筐上方 → 穿越中心线 → 球在篮筐下方」的连续帧序列。两阶段精扫虽然使用全帧，但**精扫触发依赖粗扫的候选区间是否正确定位**——形成循环依赖，无法根本解决。

#### 瓶颈 2：遮挡时 IOU 追踪器轨迹断裂 🔴

野球场篮下对抗激烈，球在最接近篮筐的关键时刻（最易被球员遮挡）最容易追踪丢失。当前 IOU Tracker 的 `predict_position` 使用**线性外推**，而篮球实际遵循抛物线运动（含重力加速度），预测误差随帧数增加快速放大，遮挡 3~5 帧后无法重新关联。

#### 瓶颈 3：通道 4（Farneback 光流）无法区分进球与篮板争抢 🟡

当前通道 4 计算篮网 ROI 区域内的**平均运动幅度**，无法区分：
- 进球：球从上到下穿网，垂直向下运动占主导
- 篮板争抢：多人激烈争抢，横向运动杂乱，幅度同样很大

单独依赖通道 4 的误报率天然偏高，这是设计层面的局限，调参无法根本解决。

#### 瓶颈 4：通道 2（人体运动）与通道 3（帧差分）信噪比过低 🟡（通道3已缓解）

这两个通道是纯启发式规则，在激烈对抗中频繁触发误报。跨通道互证（v2.4）限制了单通道 boost。

**T-1.9.14 已缓解通道3问题**：
- 通道3置信度上限从 0.50 降至 **0.35**，计算公式也从 `min(0.50, 0.3+0.05*r)` 调整为 `min(0.35, 0.2+0.04*r)`
- 通道3现在仅作为**候选触发信号**（帮助定位候选区间），不再作为独立进球信号
- 即使被跨通道互证 boost，受 `WEAK_CHANNEL_CAPS` 限制也不会超过 0.35

通道2仍维持现有逻辑，后续可通过算法A（ROI多帧分类器）进一步改善。

### 12.3 策略评估：调优现有算法 vs 引入新算法

**结论：应同时推进，新算法优先级高于继续调参。**

调优已接近天花板：
- 阈值、冷静期、互证窗口已系统性调整（O-2、O-6、O-11）
- 继续微调参数只有边际改善，无法解决上述结构性瓶颈
- 真正的提升来自**针对野球场物理特性设计的新算法**

### 12.4 推荐引入的新算法

#### 算法 A：篮筐 ROI 多帧堆叠分类器（优先级：P1，长期最高价值）

**原理**：以篮筐为中心裁剪 2× 扩展 ROI，将连续 N 帧（约 8~15 帧，覆盖 ~1 秒）在通道维度堆叠，输入轻量级分类网络，直接输出「进球 / 未进」概率。

```python
def classify_goal_roi(frames: List[np.ndarray], hoop_rect: Tuple,
                      model, n_frames: int = 12) -> float:
    """
    以篮筐为中心裁剪 2x 扩展 ROI，堆叠 n_frames 帧。
    输入: (H, W, n_frames*3) 张量
    输出: goal_probability [0, 1]

    参考: 专利 CN202411951718《基于视频输入的实时篮球进球检测识别方法》
    """
    roi_frames = [crop_expand(f, hoop_rect, ratio=2.0) for f in frames]
    roi_frames = [cv2.resize(f, (128, 128)) for f in roi_frames]
    stacked = np.concatenate(roi_frames, axis=-1)  # (128, 128, n*3)
    prob = model.predict(stacked[np.newaxis])[0]
    return float(prob)
```

**为何对野球场特别有效**：
- 野球场固定单机位 → 篮筐位置稳定 → ROI 裁剪高度可靠
- 模型自动学习时序特征（球穿越的光流模式），无需手工规则
- 即使球被遮挡，篮网形变、光照变化等时序信号也被模型隐式捕捉
- 只需 **300+ 标注片段**（进球 / 未进各半）即可训练出可用模型

**实施路径**：
1. 收集真实野球场进球片段（200~500 个），以篮筐 ROI 为中心裁剪
2. 用 MobileNetV3-Small 或 EfficientNet-Lite0 微调
3. 作为新的**通道 6**接入，置信度上限 0.90
4. 现有通道 1a~1b 降权，以通道 6 为主判定信号

#### 算法 B：物理模型 Kalman 轨迹补全（优先级：P1，近期可落地）

**原理**：用 Kalman Filter 替代当前 IOU Tracker 的线性预测，在状态转移矩阵中引入重力加速度，使预测轨迹遵循抛物线。遮挡 3~8 帧后仍能可靠预测球位置，大幅提升通道 1a 在遮挡场景下的召回率。

```python
class PhysicsKalmanTracker:
    """
    状态向量: [x, y, vx, vy]
    转移矩阵: vy += g_per_frame（重力加速度分量）

    vs 当前 IOU Tracker: predict_position 为纯线性外推
    新版: 抛物线预测，遮挡后可维持 3~5 帧有效预测
    """
    def __init__(self, fps: float = 3.0):
        import cv2
        self.kf = cv2.KalmanFilter(4, 2)  # 状态4维，观测2维
        g_per_frame = 9.8 / (fps ** 2) * 50  # 像素单位重力
        self.kf.transitionMatrix = np.array([
            [1, 0, 1, 0],
            [0, 1, 0, 1],
            [0, 0, 1, 0],
            [0, 0, 0, 1],
        ], dtype=np.float32)
        self.gravity = g_per_frame  # 每次 predict 后 vy += gravity
```

**涉及文件**：`ai-engine/tracker.py`——在 `IOUTracker` 类中升级 `predict_position` 方法，或新增 `PhysicsKalmanTracker` 类作为可选追踪器。

#### 算法 E：因果推理链验证器（优先级：P0，零训练成本）

**核心思想**：篮球进球不是孤立事件，而是一个**时间因果链**。真实进球前必有「前因」（投篮动作/球体运动），后必有「后果」（庆祝反应/音频事件）。通过检查候选事件前后的因果信号是否存在，可以有效区分真正进球与孤立噪声事件。

**三种进球方式的因果链模型**：

篮球进球有三种典型方式，每种的时序因果链有所不同：

| 得分方式 | 前因信号（进球前）| 进球瞬间 | 后果信号（进球后）| 时序特征 |
|---------|----------------|---------|----------------|---------|
| **投篮（2分/3分）** | 球体抛物线上升轨迹（1~2s前）；球员投篮预备姿势 | 球穿越篮筐平面 | 入网声（0~0.3s后）；欢呼/叫好声（0.5~3s后）；球员急停观望（0.5~2s后） | 球从远处飞入，**进球前球体运动信号持续时间较长**（1~2s），球员不在篮筐正下方 |
| **上篮** | 球员快速接近篮筐（1~3s前）；人体位置上移；球体短距离运动 | 球近距离投入/扣入 | 同上，但欢呼反应可能更激烈 | **人体运动信号更强**（接近篮筐），球体轨迹短、持续时间短（<1s） |
| **罚球** | 球员站定不动（2~5s前）；画面相对静止 | 球穿越篮筐 | 欢呼/掌声（1~3s后）；画面恢复活动 | **前因安静**（场面静止），后果温和（非对抗），是最独特的模式 |

**因果评分算法**：

```python
def evaluate_causal_chain(candidate_event: Dict,
                          all_events: List[Dict],
                          video_duration: float) -> Tuple[float, str]:
    """
    评估候选进球事件的因果链完整性。

    返回:
        (causal_score, goal_type)
        - causal_score: 因果链完整性分数 [-0.15, +0.12]
          正值 = 因果链完整（提升置信度）
          负值 = 孤立噪声（降低置信度）
        - goal_type: 推测的进球类型 "shot" / "layup" / "free_throw" / "unknown"
    """
    t = candidate_event["timestamp"]

    # 搜集前因信号
    precursor_count = 0
    has_ball_motion = False
    has_person_motion = False

    for sig_name, sig_cfg in PRECURSOR_SIGNALS.items():
        w_start, w_end = sig_cfg["window"]
        for other in all_events:
            if other is candidate_event:
                continue
            dt = other["timestamp"] - t
            if w_start <= dt <= w_end:
                detail = other["detail"].split(":")[0].strip()
                paren = detail.find("(")
                if paren > 0:
                    detail = detail[:paren]
                if detail in sig_cfg["sources"]:
                    precursor_count += 1
                    if sig_name == "ball_motion":
                        has_ball_motion = True
                    elif sig_name == "person_motion":
                        has_person_motion = True
                    break

    # 搜集后果信号
    consequence_count = 0
    has_audio = False
    has_celebration = False
    has_net = False

    for sig_name, sig_cfg in CONSEQUENCE_SIGNALS.items():
        w_start, w_end = sig_cfg["window"]
        for other in all_events:
            if other is candidate_event:
                continue
            dt = other["timestamp"] - t
            if w_start <= dt <= w_end:
                detail = other["detail"].split(":")[0].strip()
                paren = detail.find("(")
                if paren > 0:
                    detail = detail[:paren]
                if detail in sig_cfg["sources"]:
                    consequence_count += 1
                    if sig_name == "audio_reaction":
                        has_audio = True
                    elif sig_name == "celebration":
                        has_celebration = True
                    elif sig_name == "net_deform":
                        has_net = True
                    break

    # 推测进球类型
    if has_person_motion and not has_ball_motion:
        goal_type = "layup"       # 有人体运动无远距离球飞行 → 上篮
    elif has_ball_motion and not has_person_motion:
        goal_type = "shot"        # 有球飞行无人体接近 → 投篮
    elif precursor_count == 0 and consequence_count >= 1:
        goal_type = "free_throw"  # 前因安静但后果存在 → 可能罚球
    else:
        goal_type = "unknown"

    # 因果评分
    total_signals = precursor_count + consequence_count

    if total_signals >= 3:
        causal_score = +0.12       # 强因果链：多个前因+后果
    elif total_signals == 2:
        causal_score = +0.08       # 中等因果链
    elif total_signals == 1:
        causal_score = +0.0        # 单信号：不加不减
    else:
        # 完全孤立事件：前后均无因果信号 → 降低置信度
        causal_score = -0.15       # 惩罚：大概率是噪声

    return causal_score, goal_type
```

**边界条件处理**：

| 场景 | 处理策略 |
|------|---------|
| 候选事件在视频开头 3s 内 | 前因窗口被截断 → 不惩罚前因缺失，仅评估后果 |
| 候选事件在视频结尾 3s 内 | 后果窗口被截断 → 不惩罚后果缺失，仅评估前因 |
| 同一事件同时是另一事件的前因/后果 | 不能自证 → 每个候选只搜索**其他**事件作为证据 |
| 连续快攻进球（间隔 <5s）| 前一个进球的后果信号可能与后一个的前因重叠 → 允许信号复用 |
| 通道较少（如 minimal 模式仅 1a+1b）| 因果信号来源有限 → 孤立惩罚减半（-0.08 而非 -0.15）|

**与现有跨通道互证的区别**：

| 维度 | 跨通道互证（现有） | 因果推理链（新增） |
|------|------------------|------------------|
| 时间关系 | ±2s **同时**发生 | 有严格的**先后顺序**（前因在前，后果在后） |
| 信号角色 | 所有通道平等互证 | 区分前因/进球/后果三种角色 |
| 调整方式 | 仅提升（boost）| 双向调整：提升或**惩罚** |
| 判断维度 | 空间重叠（同一时间点附近） | **时序因果**（事件发生的逻辑顺序） |
| 执行阶段 | 跨通道互证阶段（合并前） | 跨通道互证之后、事件合并之前 |

**集成位置**：在 `detect.py` 的跨通道互证之后、`merge_events_with_cooldown` 之前插入因果验证环节：

```
所有通道候选事件
    │
    ▼
跨通道互证（±2s boost）       ← 现有
    │
    ▼
因果推理链验证（前因/后果检查） ← 新增：O-23
    │  +0.12（强因果） / +0.08（中等） / -0.15（孤立噪声）
    ▼
事件合并 + 冷静期过滤          ← 现有
    │
    ▼
最终输出
```

**为何对野球场特别有效**：

- 野球场最大的误报来源是**孤立噪声事件**：击掌声误报（通道5）、运动突变误报（通道3）、偶发光流噪声（通道4）
- 这些孤立事件的共同特征是**前后没有因果信号**——没有球飞行轨迹、没有庆祝反应
- 因果链的 -0.15 惩罚可以将这些噪声事件的置信度压低到阈值以下，直接过滤
- 同时，真正的进球通常有 2~3 个因果信号伴随，获得 +0.08~+0.12 的提升

**实施成本**：

- **零训练成本**：纯逻辑实现，不需要任何模型训练或数据标注
- **代码改动量**：新建 `ai-engine/causal_chain.py`（~200 行）+ `detect.py` 插入 ~15 行调用代码
- **运行时开销**：仅遍历已有候选事件列表，无额外推理，耗时可忽略
- **风险**：极低——仅对置信度做微调（±0.15），不改变通道检测逻辑，可通过配置开关关闭

**涉及文件**：新建 `ai-engine/causal_chain.py`；修改 `ai-engine/detect.py`（跨通道互证后插入因果验证调用）。

#### 12.8.1 O-10 篮球专用 YOLO 模型——最根本的源头优化

**评估结论：P1 级，应与算法 B（Kalman 追踪）同步推进，优先于算法 A（ROI 分类器）。**

**问题根源**：

当前使用 YOLOv8n COCO 预训练模型，检测 class 32（`sports ball`）。COCO 的 `sports ball` 类别包含篮球、足球、网球、排球等所有球类，**非篮球专用**。更关键的是，模型根本没有 `hoop`（篮筐）类，`HoopDetector` 的策略 1（YOLO 检测篮筐）实际上**永远不会命中**，系统实际运行的只有策略 2/3/4（颜色形状/球体热力图/固定比例回退）。

**影响链**：YOLO 检测质量是所有通道的上游基础：

```
YOLO检测质量不足
    ├── 球体检测率低 → 通道1a轨迹断裂 → 几何判定失效
    ├── 球体误检（非篮球）→ 追踪器被噪声污染 → 假轨迹
    ├── 篮筐无法检测 → HoopDetector 回退到颜色/比例策略 → 篮筐位置不准
    └── 无 net 类 → 通道4/算法C 的网区ROI只能靠篮筐位置推算
```

**推荐数据集**：

| 数据集 | 图像量 | 标注类别 | 说明 |
|--------|--------|---------|------|
| Roboflow Basketball Detection | ~3,500+ 图像 | basketball / hoop / person | 最常用，质量高 |
| Basketball Video Analysis (Roboflow) | ~5,000+ 图像 | basketball / hoop / net / player | 含 net 类别，最完整 |
| NBL/CSBL 开源标注数据 | 按版本 | basketball / rim | 部分含 rim 类 |

推荐直接从 Roboflow Universe 搜索 `basketball` 下载 YOLOv8 格式，合并多个数据集后微调，目标四类：`basketball / hoop / net / player`。

#### 12.8.2 VLM 辅助确认通道（通道 7）——唯一具备语义理解的在线过滤器

**评估结论：P1 级，与算法 B/O-10 并行推进。与现有 VLM 验证器（评估工具）有本质区别。**

**与现有 VLM 验证器的区别**：

| 维度 | 现有 VLM 验证器（`vlm-verification.md`）| 新通道 7：VLM 确认通道 |
|------|----------------------------------------|----------------------|
| 用途 | **离线评估工具**：衡量算法准确率，输出 P/R/F1 | **在线过滤器**：集成进检测 pipeline |
| 调用时机 | 算法运行完之后，独立批量扫描 | 算法运行中，对候选事件实时调用 |
| 调用量 | 全视频扫描：~2700 窗口 / 90min 视频 | **仅候选事件**：约 10~30 次 / 视频 |
| 成本 | ~$27 / 90min 视频（GPT-4o）| **~$0.10~0.30 / 视频**（GPT-4o）|
| 输出 | 评估报告（feedback.json） | 每个候选的置信度分数 → 融合到最终判定 |

**核心工作模式（高 Recall 候选 → VLM 过滤 → 输出）**：

```
通道1a~6（高Recall模式）
    │  降低各通道阈值，大量产生候选事件
    │  置信度区间：[0.30, 0.55)（低于最终输出阈值）
    │
    ▼
候选事件队列（预计 15~50 个 / 视频）
    │
    ▼
通道7：VLM 确认通道
    ├── 裁剪候选事件 ±4s 的视频片段
    ├── 均匀抽取 8 帧
    ├── 调用 VLM：「这组帧中篮球是否进入篮筐？」
    └── 返回 VLM 置信度 [0, 1]
    │
    ▼
VLM 置信度融合（权重 0.80）
    │  最终置信度 = max(原算法置信度, VLM置信度 * 0.80)
    │  OR: 两者 AND 双重确认模式（Precision 优先）
    │
    ▼
最终输出（阈值 0.55）
```

**具体实现**：

```python
class VLMConfirmChannel:
    """
    通道 7：VLM 候选事件确认。
    复用 test/vlm_verify/verify_vlm.py 中的 VLMReviewer 类，
    调整为单片段确认模式（而非全视频扫描）。
    """

    def __init__(self, provider='ollama', model='llava:13b'):
        # 优先 Ollama 本地模型（免费），无 API 依赖
        # 生产环境可切换 gemini/gpt-4o
        self.reviewer = VLMReviewer(provider=provider, model=model)

    def confirm(self, video_path: str, candidate_ts: float,
                context_seconds: float = 4.0) -> float:
        """
        对单个候选事件调用 VLM 确认。
        返回 VLM 给出的进球置信度 [0, 1]。
        """
        clip_path = extract_clip(video_path, candidate_ts, context_seconds)
        frames = sample_frames(clip_path, n=8)
        result = self.reviewer.review_clip(frames)
        return result.get('confidence', 0.0)

    def batch_confirm(self, video_path: str,
                      candidates: List[float]) -> List[float]:
        """批量确认，可并发调用（Ollama 本地推理时无 rate limit 限制）"""
        with ThreadPoolExecutor(max_workers=2) as executor:
            return list(executor.map(
                lambda ts: self.confirm(video_path, ts), candidates
            ))
```

**两种工作模式**：

| 模式 | 触发条件 | 适用场景 |
|------|---------|---------|
| **Precision 优先**（AND 双确认）| 算法置信度 ≥ 0.55 才输出，同时要求 VLM 置信度 ≥ 0.60 | 误报成本高的场景（正式比赛） |
| **Recall 优先**（OR 宽松补充）| 算法置信度 0.35~0.55 的候选，若 VLM ≥ 0.70 则加入输出 | 漏检成本高的场景（野球场集锦） |

**本地 Ollama 优先**：使用 `llava:13b` 本地模型时，VLM 调用完全离线，无 API 成本，也不依赖网络。系统检测到无 `VLM_API_KEY` 时自动降级为 Ollama；Ollama 未安装时此通道静默跳过，不影响现有流程。

**为何对野球场特别有效**：野球场进球场景的多样性（角度各异、遮挡程度不同、照明条件变化）超过任何规则系统的设计边界。VLM 的端到端视觉理解能力使其天然适应这种多样性，而规则系统只能应对被预见的场景。

#### 12.8.3 双篮筐 / 多篮筐检测——全场视角下的完整覆盖

**评估结论：P2 级，优先级低于 O-10/VLM/算法B，但对全场比赛视频是必要功能。**

**问题场景**：

当摄像机架设于场地中线附近或较高位置时，画面中同时出现两端篮筐：

```
摄像机视角（全场俯视）：

   左篮筐  ────────────────────  右篮筐
      ○                               ○
      │           球场区域             │
```

当前 `HoopDetector` 的 `_detect_hoop_color` 和 `_detect_hoop_yolo` 只返回**单个**篮筐（置信度最高的），导致：
- 如果球员在远端篮筐进球，近端篮筐被检测，远端进球被漏检
- 如果两端都有得分，只有一端被记录

**野球场的实际频率**：
- 半场游戏（打半场）：摄像机通常朝向单侧 → **不受影响**（主要场景）
- 全场游戏（打全场）：摄像机可能包含两端 → **受影响**（较少见）

**实现方案**：

```python
class HoopDetector:
    """扩展为支持多篮筐检测"""

    def detect_all_hoops(self, frame_files, model=None,
                         ball_detections=None) -> List[Tuple]:
        """
        返回所有检测到的篮筐列表，按置信度降序。
        每个篮筐: (cx, cy, w, h, confidence, side)
        side: 'left' / 'right' / 'single'（根据画面位置推断）
        """
        hoops = []
        # ... 检测所有候选篮筐
        # 根据 cx 位置判断 side
        for hoop in hoops:
            cx = hoop[0]
            hoop['side'] = 'left' if cx < self.img_w * 0.4 \
                           else ('right' if cx > self.img_w * 0.6 \
                           else 'center')
        return hoops

def assign_ball_to_hoop(ball_pos: Tuple, hoops: List) -> Tuple:
    """
    当多个篮筐存在时，将球的轨迹点分配给最近的篮筐。
    考虑球的运动方向（向哪端运动）来优化分配。
    """
    if len(hoops) == 1:
        return hoops[0]
    distances = [dist(ball_pos, h[:2]) for h in hoops]
    return hoops[min(range(len(hoops)), key=lambda i: distances[i])]
```

**每个篮筐独立建立检测区域**，球追踪时根据球的位置动态分配到最近篮筐，每个篮筐独立触发进球判定。

**优先级说明**：
- 野球场半场游戏（最常见场景）完全不需要此功能
- 此功能对正式比赛（全场、固定机位）更有价值
- 建议在 O-10（专用 YOLO，可识别多个 hoop）完成后顺带实现，开发成本可控
